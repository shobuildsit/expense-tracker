# Setup

This project has two halves: a small Python poller (`messages_watcher/`) that runs on
your Mac, and a set of Make.com scenarios that do the parsing/logging. Neither half is
committed to this repo with real credentials — you'll plug in your own.

## 1. Google Sheets

Create a spreadsheet with a `Transactions` sheet (Google Sheets' native "Table" feature
works well here, since it gives you per-column formatting and dropdowns for free).
The shipped blueprints expect this exact **A–J** layout:

| Col | Column | Type | Notes |
|---|---|---|---|
| A | `ID` | text | Unique per transaction, generated by Make (`formatDate(now; "YYYYMMDDHHmmssSSS")`) |
| B | `Date` | date | |
| C | `GEL` (or your base currency) | currency | The parsed transaction amount |
| D | `JPY` (or your target currency) | currency | Converted amount |
| E | `Merchant` | text | |
| F | `Category` | dropdown | One of the categories used in the OpenAI prompt (Transport, Food, Cafe, …) |
| G | `Status` | dropdown | `Pending` / `Done` |
| H | `Description` | text | Reserved for the OpenAI parser's `description` field. Add the header so the column exists, but note the shipped blueprints do not currently write to it — no scenario maps a value into `Description` yet. |
| I | `Reserved` | text | Reserved for future use. Keep the header so the native Google Sheets table remains a contiguous A–J range; leave row values blank. |
| J | `Source Event ID` | text | Stable per-event ID (Gmail message ID for Wise, Messages GUID for BOG). Checked before logging to avoid re-adding the same transaction on a retry/redelivery — see [Idempotency](#idempotency--duplicate-prevention) below. |

> If you're using Google Sheets' Table feature, make sure the currency columns'
> column type is set to **Currency**, not plain **Number** — plain Number columns
> won't pick up the currency symbol/decimal formatting on rows added via the API.

> Column letters matter here: the `filterRows`/`addRow` modules address columns E–J by
> letter (`"a": "E"`, `"a": "J"`, …), not just by header name. If your sheet doesn't
> match A–J exactly, update the column letters in the affected modules after import.

Scenario 2 also needs one helper cell outside the `Transactions` table. Put this formula
in **`Dashboard!Z1`**:

```gs
=COUNTIF(Transactions!G2:G,"Pending")
```

Scenario 2 reads this value with `google-sheets:getCell` when another pending expense
remains, then shows it in the LINE message as `Pending: {value}`. The Blueprint reads
the cell but does not create the formula. If `Dashboard!Z1` is already in use, choose
another helper cell and update module 15 in Scenario 2 to match.

## 2. Make scenarios

There are three scenarios, and they are not interchangeable — each has a distinct role:

| Scenario | Role | Needs |
|---|---|---|
| **Scenario 1 — Wise Expense Logger** | Watches Gmail for Wise payment emails, parses them with OpenAI, checks/records `Source Event ID`, and writes rows to the `Transactions` sheet. | Gmail connection, Google Sheets connection, OpenAI connection. |
| **Scenario 2 — LINE category handler** | Not an ingestion source — it's the *shared* handler for the "tap a category" flow. Reacts to LINE postback taps, updates the tapped row (`Status=Done`, `Category=<picked>`), then either sends a "all done" confirmation or looks up the next `Pending` row and prompts for it. | LINE connection (Messaging API), Google Sheets connection. Only needed if you use the LINE category-prompt flow at all — i.e. if either Scenario 1 or 3 is active and can produce a `Pending` row. |
| **Scenario 3 — BOG SMS Expense Logger** | Receives BOG SMS text (forwarded by `messages_watcher` or a direct webhook call) via a Custom Webhook, parses it with OpenAI, checks/records `Source Event ID`, and writes rows to the `Transactions` sheet. | Custom Webhook, Google Sheets connection, OpenAI connection. |

What you need to import depends on which sources you actually use:

- **Wise only:** Scenario 1 (+ Scenario 2 if you want the LINE category prompt for new merchants).
- **BOG only:** Scenario 3 (+ Scenario 2, same reason) and `messages_watcher` (see step 3 below).
- **Both Wise and BOG:** Scenario 1 + Scenario 3, sharing a single Scenario 2 — don't import or fork a second copy of Scenario 2, both ingestion scenarios are meant to hand off to the same one.
- **No LINE category flow at all:** Scenario 2 isn't needed, but then new merchants have no way to get a category — every new-merchant row will sit at `Status=Pending` indefinitely. This is a real trade-off, not a recommended setup.

Import whichever sanitized blueprint(s) from [`make/examples/`](../make/examples/) match what you need, then reconnect the pieces that can't be exported with real credentials:

1. **Connections** — reselect your Google Sheets / Gmail / OpenAI / LINE connections in
   each module that shows a broken connection after import.
2. **Google Sheets spreadsheet** — every `google-sheets:*` module needs to point at
   the spreadsheet you created in step 1.
3. **Webhook (BOG scenario only)** — the trigger module ships with no webhook
   attached. Create a Custom Webhook in Make, select it in the module, then use
   "Redetermine data structure" with a sample payload (see below) so the `message`
   field is recognized.
4. **LINE messaging (Scenario 2, and the LINE-push step of Scenarios 1/3)** — create a
   LINE Messaging API channel, put the channel access token in the HTTP module's
   `Authorization` header, and put your own LINE user ID in the `to` field. Scenario 2
   additionally needs its `line:watchMessages` trigger connected to the same channel
   (so it receives the postback events when you tap a category button) and needs the
   `Dashboard!Z1` helper formula described above.

### BOG scenario: webhook payload shape

```json
{
  "source": "messages",
  "filter_type": "sms",
  "sender": "4444",
  "message": "<raw BOG SMS text>",
  "guid": "<Messages DB GUID for this message>"
}
```

`message` is parsed by OpenAI; `guid` is used as the Source Event ID for duplicate
prevention (see below) — make sure your sample payload includes it before running
"Redetermine data structure", or the dedup lookup module will have nothing to map.
A sample BOG SMS body (dummy data) is in
[`samples/sample_bog_sms.txt`](../samples/sample_bog_sms.txt) — useful for testing the
webhook directly with `curl` before wiring up `messages_watcher`.

### JPY conversion (BOG scenario)

BOG SMS never includes a JPY amount, so the BOG scenario computes it with a fixed
rate (`round(gel * 62)` in the shipped blueprint — edit the `62` to your own rate).
The Wise scenario instead relies on the email body / model estimate, unchanged.

### Idempotency / duplicate prevention

Two independent checks run for every incoming transaction, and they do different jobs:

- **Event-level deduplication (`Source Event ID` column).** Before parsing with
  OpenAI, each scenario checks its `Source Event ID` (the Gmail message ID for Wise,
  the Messages GUID for BOG) against the existing rows in column J. If a match
  exists, the scenario stops silently — no new row, no LINE message, no error. This
  is a check-then-insert pattern: it prevents duplicate rows during normal retries,
  redelivery, or manual re-execution (Gmail redelivering a message, `messages_watcher`
  resending after a restart, re-running the scenario by hand in Make). It is
  application-level duplicate prevention, not an atomic uniqueness guarantee — it does
  not protect against two executions for the *same* Source Event ID racing each other
  at the exact same instant. For a personal, low-volume automation like this one,
  that gap is not expected to matter in practice.
- **Known-merchant classification (`Merchant` + `Status=Done` lookup).** Separately,
  once a transaction is confirmed genuinely new, the scenario checks whether this
  *merchant* has a prior `Done` row so it can reuse the category instead of prompting
  you over LINE again. This has nothing to do with duplicate transactions — the same
  merchant is expected to appear many times, each as its own row.

**If the Source Event ID is missing.** The dedup lookup module itself only runs when
the incoming ID (`{{2.id}}` for Wise, `{{1.guid}}` for BOG) is non-empty — this is a
deliberate guard, not an oversight: without it, a missing ID would search column J for
`""`, match any row that doesn't have a `Source Event ID` yet (e.g. rows added before
this column existed), and either get wrongly treated as a duplicate, or — if no such
row exists — get logged with a blank `Source Event ID` that would then wrongly match
*every future* ID-less event. Instead, if the ID is empty, the whole scenario run
stops right there: no dedup lookup, no OpenAI parsing, no row, no LINE message. This
is not expected to trigger in normal operation (Gmail and the Messages database always
provide an ID), but if it ever does, the event is dropped rather than misfiled — check
that scenario's execution history in Make if a transaction seems to be missing.

## 3. messages_watcher (only needed for the SMS/iMessage source)

```bash
cd messages_watcher
pip install -r requirements.txt
cp .env.example .env
```

Edit `.env`:

```env
MAKE_WEBHOOK_URL=<the webhook URL from step 2.3>
MESSAGE_FILTER_TYPE=sms
MESSAGE_FILTER_VALUE=<the sender to watch — e.g. a bank's SMS short code>
```

Grant your terminal app **Full Disk Access** (System Settings → Privacy & Security →
Full Disk Access), then run:

```bash
python3 watcher.py
```

See [`messages_watcher/README.md`](../messages_watcher/README.md) for the full
options list, including `DRY_RUN` and `INCLUDE_FROM_ME` for local testing without
touching your production Make scenario.

## 4. Test end to end

1. In Make, open the BOG scenario's webhook module and click **Run once**.
2. POST the sample payload directly:
   ```bash
   curl -X POST "<your webhook URL>" \
     -H "Content-Type: application/json" \
     --data-binary @- <<EOF
   {"source":"messages","filter_type":"sms","sender":"4444","message":"$(cat samples/sample_bog_sms.txt)","guid":"test-guid-001"}
   EOF
   ```
3. Confirm a row was added to your Transactions sheet (with `test-guid-001` in the
   `Source Event ID` column), and (if configured) that a LINE message with category
   buttons arrived. POSTing the exact same payload again should add **no** second row.
4. Once you're satisfied, switch `messages_watcher`'s `.env` to your real sender and
   run it for real.
